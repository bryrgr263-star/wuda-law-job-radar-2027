# Multi-target endpoint execution

An Endpoint is one source execution boundary, not one authorization. Its approved continuous acquisition scope enumerates the exact targets required for complete coverage. The adapter's ordered request plan must contain exactly those targets. A separate, current continuous authorization is required for each request; neither the scheduler nor the adapter can authorize a sibling URL.

Before sending a request, the Production Root seals and commits an immutable `SourceExecutionRequestIntent` under `production-runs/source-request-intents/`. It binds the source revision, endpoint and admission artifacts, ordered exact URLs, allowlist revisions, purpose, request policy, and selected authorization IDs. A retry may reuse identical bytes; changed bytes under the same source-execution ID are rejected. Each request still enters the existing continuous gate, reservation, cadence, and revocation checks immediately before transport.

The sealed `SourceExecutionOutcome` contains a per-target observed request plan with attempt, acquisition, RawBlob, Snapshot, and ExtractedRecord references. Process B verifies the intent, every target binding, observed acquisition evidence, and the outcome-to-intent correspondence. An incomplete or failed target cannot become source `SUCCESS`, `NOT_MODIFIED`, or `CONFIRMED_EMPTY`. A crash after a reservation leaves the intent and continuous records committed, but no invented outcome; scheduling stops until the existing fencing/recovery contract resolves the pending attempt.

`SourceAdmission.endpoint_purpose` is the authoritative purpose. An allowlist target must carry that same purpose. The historical Zhenghan Canary allowlists use page-specific purpose labels, so they cannot serve as continuous production authority. Initial source activation preserves those historical revisions, appends reviewed SourceAdmission and allowlist revisions, and issues a separate committed authorization per exact target. It does not access official sites or enable the workflow.

Single-target historical scheduler manifests and source outcomes remain readable. New multi-target manifests use schema v2; new continuous source outcomes carry the sealed request plan. No new Recall, Relevance, Requirement, Eligibility, or Presentation authority is introduced.
